# pivotkit-core

The engine. Plain JavaScript ES modules with JSDoc types. No UI, no framework.
The root [AGENTS.md](../../AGENTS.md) applies too.

## Commands

```bash
npm test -w pivotkit-core        # node --test
npm run coverage -w pivotkit-core
npm run types -w pivotkit-core   # type check and generated .d.ts in types/
npm run bench -w pivotkit-core   # engine timings
node scripts/schemas.js          # rebuild schema/ after a table change
```

`types/` is generated, not committed. Run `npm run types` before a later package imports the core.

## Entry points

- Public: `src/index.js`, `export.js`, `chart-style.js`, `link.js`, `templates.js`, `import.js`.
- Every other module is internal.
- `src/internal.js` (`pivotkit-core/internal`) shares helpers with this repository's packages. It is no public API: docs never name it.
- A new public function is exported from an entry and listed in `test/api.test.js`.
- Also document it in `docs/reference/core.md`.
- Only the export and link entries import `fflate`. `test/api.test.js` checks it.
- The main entry never reaches the import modules. `test/api.test.js` checks it too.
- The import entry loads a reader's code only when a file is read.

## Dependencies

- The only runtime dependency is `fflate`, for the XLSX zip. Keep it that way.
- Write the XLSX XML by hand. No SheetJS, no ExcelJS.
- Build plain ECharts option objects. Never import ECharts.
- `src/` uses only globals that browsers and Node share. ESLint's `no-undef` with `shared-node-browser` globals enforces it.

## The view

- The vocabulary lives in tables: `AGGREGATORS`, `DERIVED`, `FILTERS`, `SHOW_AS`.
- `CATALOG` lists them for a UI, so a new entry needs no UI change.
- How to add an aggregator, filter type or view key: [Adding a view feature](#adding-a-view-feature).
- The view is version 2 (`VIEW_VERSION`). `MIGRATIONS` in `view.js` holds the step from version 1.
- `test/v1-corpus.js` with `test/v1-golden.json` proves every version-1 view keeps its rows.

## View files and schemas

- `view-file.js` is the one format a view is shared in: file, JSON or link.
- It writes view file version 2 and reads 1 and 2.
- `schema/*.json` is generated by `scripts/schemas.js`. `tests/schemas.test.js` checks it.
- Keep `schema/view-file-1.json` for files of version 1.

## Issues and limits

- Every issue of `normalize()` and `computePivot()` has a code of `VIEW_ISSUES` in `view.js`.
- A new kind of issue needs three things:
  - its code in `VIEW_ISSUES`
  - its case in `test/issue-cases.js`
  - its texts in pivotkit-react's `unused-texts*.js`
- `LIMITS` in `limits.js` bounds every structure that grows. Over a limit is `LIMIT_EXCEEDED`.
- Counted limits: `rows` in `encode`, `work` before `computePivot`, `groups`, `pivotCells`, `cells`.
- `work` is rows x (row fields + 1) x (column fields + 1) x measures.
- Views from outside use `OUTSIDE_LIMITS` through `outsideLimits()`.

## One place for each rule

Reuse these instead of writing a second version:

| Concern | Where |
| --- | --- |
| Text folding for search and filters, without the runtime's locale | `foldText` in `text-match.js` |
| "Did you mean" hints | `closest` in `hints.js` |
| Relative date ranges | `rangeOf` in `relative.js` |
| A view from field names or a layout | `viewFromLayout` in `suggest.js` |
| Which fields are identifiers | `isIdentifierName` in `suggest.js` |
| The date unit for a span | `dateUnitFor` in `derive.js` |
| Every place a view names a field | `mapFieldRefs` in `view-file.js` |
| A loaded file's source id | `sourceIdOf` in `source-id.js` |
| Grouping names and report words, en and de | `GROUPING_NAMES`, `REPORT_LABELS` in `labels.js` |
| Chart data and the type "auto" stands for | `toSeries`, `autoChartType` in `chart-series.js` |
| The ECharts option, loaded with the chart | `toEChartsOption` in `chart.js`, also exported by `chart-style.js` |
| Chart marks for screen, SVG and print | `decorateOption` in `chart-style.js` |
| Which chart draws which reference line, and whether a value adds up | `referenceLineRules`, `valueAddsUp` in `chart-plan.js` |
| A chart's reference lines as numbers | `referenceLines` in `chart-lines.js` |
| Chart theme fallbacks | `DEFAULT_THEME` in `defaults.js` |
| Bounded caches | `createCache` in `util.js` |

- Column names match case-insensitively. Display keeps the data's own spelling.
- `schema.js` reads field defaults from a JSON Schema. Only local `$ref`s, nothing fetched.
- Schema sizes are capped by `SCHEMA_CAPS`.

## Readers

A loaded file is user input. Every reader follows these rules:

- Count what a file can grow against `LIMITS` before the step it guards.
- That means: the size before reading, an archive's directory before unpacking, rows while reading.
- Refuse what a table never needs: macros, `<!DOCTYPE`, encrypted or old binary workbooks.
- Say what to do instead.
- Build the table with `createTable` in `import-table.js`. Every format is cleaned the same way.
- Start no worker of your own. A strict CSP blocks `blob:` workers.
- Errors are `INVALID_FILE` with `details.reason`, or `LIMIT_EXCEEDED` with `details.file`.

### Reader fixtures

- Test on real files: `test/import-fixtures/`. Each has its source and licence in `SOURCES.md`.
- Keep fixtures byte for byte. `.gitattributes` protects them.

## Exports

- Exports must be safe to open.
- CSV text a spreadsheet would run as a formula gets a leading `'`. The rule is in `src/csv.js`.
- The clipboard copies use the same guard.
- XLSX writes text as inline strings, never as formulas.
- CSV, TSV, XLSX, HTML and SVG leave out bidi controls (`BIDI_CONTROLS` in `src/csv.js`).

## Performance

- The engine is measured up to 1,000,000 rows. Use typed arrays.
- No per-row objects in hot loops.
- Run `npm run bench` before and after an engine change.
- Compare with the baseline in `docs/reference/core.md` (Performance).

## Tests

- Test through the public API. Import an internal module only when the API cannot reach it.
- Shared rows are in `test/fixtures.js`.
- Behaviour that depends on the machine runs in child processes with `TZ` and `LANG` set.
- See `test/time-zones.test.js` for the pattern.
- A type change: `test/types/consumer.ts` must compile against the generated declarations.

## Adding a view feature

A new name is one table entry plus its tests:

| Feature | Table | Also |
| --- | --- | --- |
| Aggregator | `AGGREGATORS` in `aggregators.js` | its label in `DEFAULT_LABELS.aggregators` |
| Date grouping or bin unit | `DERIVED` in `derive.js` | |
| Filter type | `FILTERS` in `filters.js` | |
| "Show values as" | `SHOW_AS` in `show-as.js` | |
| Format | `FORMAT_NAMES` and `formatterFor` in `format.js` | its Excel code in `excelNumberFormat` |
| View key | a section in `view.js`, in `SECTIONS` and `emptyView()` | a migration if old views change |

- An aggregator that stores a value per row sets `keepsValues`. It counts heavier against `work`.
- A format without an Excel code: note the gap in `docs/concepts/values.md` (Export).
- A view key that changes old views raises `VIEW_VERSION` and adds a step to `MIGRATIONS`.
- After a table change, run `node scripts/schemas.js`.
- Then document it: `docs/concepts/views.md`, the key's concept page and `docs/reference/core.md`.
